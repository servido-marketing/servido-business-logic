## Rule
A worker (provider) MAY attach media to a task they are assigned to, through the same
mechanism used today for task photos (`addTaskMedia` / `TaskMediaAdded` event,
`providerMedia` projection field). The set of allowed media kinds is extended from
{photo, video} to {photo, video, document} — a document is any non-image/non-video
file (PDF, etc). This is a widening of the existing `Media` union
(`docs/schemas/media.schema.json`), not a new upload pathway: the same callable,
event, and projection field carry all three kinds. Attachments are additive — they
never replace or limit existing photo/video attachments already supported.

Only the assigned worker (or roles already permitted to call `addTaskMedia`, i.e.
`customer`/`provider` per `fromRole`) may add task media; the write MUST go through
the `addTaskMedia` callable, never a direct Firestore write. Deletion of media follows
the existing `deleteTaskMedia`/media-removal pathway, unchanged for the new kind.

Client picker UI (worker-facing) MUST allow choosing a photo, a video, or a document
file, and MUST determine `Document.mimeType` from the picked file and set
`Document.fileName` from its original name so it can be shown/downloaded as such
elsewhere (customer/manager task views).

## Rationale
- Reuses the exact media-union pattern already proven for the video-alongside-photo
  case (`cms-service-video-uploads`) — extending the discriminated `oneOf` union
  rather than adding a parallel documents field keeps a single ordered attachments
  list and a single upload/delete pathway.
- Workers frequently need to hand over non-image evidence (an invoice PDF, a manual,
  a signed form) alongside before/after photos — treating it as "just another media
  kind" avoids a bespoke second attachments feature.

## Implementation
- `docs/schemas/document.schema.json` (new): `{ path, fileName, mimeType, bytes }`,
  all required, `additionalProperties: false` — mirrors the shape convention of
  `photo.schema.json`/`video.schema.json`.
- `docs/schemas/media.schema.json`: `oneOf` widened to include
  `./document.schema.json` alongside `photo`/`video`.
- No new callable, event, or transaction schema needed — `addTaskMedia` /
  `TaskMediaAddedEvent` / `AddTaskMediaRequest` already carry a `media: Media` payload
  that now structurally accepts a document.
- Flutter mirrors (hand-maintained, NOT regenerated by `generate:types`) must be
  updated in lockstep: the `Media`/`MediaMetadata` model in
  `apps/packages/model/lib/src/entities/`, the wire-shape mirror in
  `apps/packages/backend/lib/src/transaction_types/transaction_types.dart`, and the
  `toFront()`/`toBack()` mapping in `apps/packages/backend/lib/src/mapping.dart` need a
  `Document` variant added alongside the existing `Photo`/`Video` variants.
- Worker-facing UI: extend the existing task-media add flow (wherever photo/video
  picking is wired for a provider on a task) with a document/file picker option;
  extend `TaskPhotoGrid`-equivalent display (or a sibling attachments list) to render
  documents (icon + file name + download link) rather than a thumbnail.

## Verification
- Worker can add a document attachment to an assigned task and it appears in the
  task's media/attachments list showing its file name.
- Existing photo and video attachment flows for a task are unaffected (regression).
- `Media.fromJson`/`toJson` round-trips a document payload without data loss on both
  CF and Flutter sides.
