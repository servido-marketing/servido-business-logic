## Rule
This applies only to NON-COMPANY (independent manager) recurring gigs. Either the
customer who owns a `recurring_bookings/{id}` series, or any independent manager
assigned to serve it, MAY cancel the series. Company-served recurring gigs are out of
scope — no company/company-manager cancel path is added by this card. Cancelling the
series ONLY stops future occurrences from being generated — it does NOT touch any
already-created occurrence tasks (those keep their existing per-task lifecycle/cancel
controls unchanged).

1. Set `recurring_bookings/{id}.status = 'cancelled'` (rolling top-up and monthly
   materialization already skip non-`active` bookings per
   `generateDueTasksForBooking`/`commitRecurringBookingForTask`, so no future occurrence
   is generated after this).
2. Existing occurrence tasks (`tasks.recurringBookingId == id`), regardless of state, are
   left completely untouched by a series cancel. Cancelling an individual already-created
   occurrence remains the existing per-task `requestCancel` flow, unrelated to this action.
3. Series cancel MUST NOT be offered when the booking is already `cancelled` or
   `completed`.

## Rationale
Today cancel only exists per-occurrence task (`requestCancel`); a customer or manager who
wants out of a recurring series has to remember to stop it, or occurrences keep
generating indefinitely. A single series-level "stop future occurrences" action is the
expected control for a subscription-like recurring gig, mirroring how
`recurring_bookings.status` already gates generation. It is intentionally NOT a bulk
cancel of already-created occurrences — those are separate bookings already in flight.

## Implementation
- `docs/schemas/recurring-booking.schema.json`: `status` already includes `'cancelled'`;
  add `cancelledAt?: Timestamp` and `cancelReason?: string`.
- New callable `cancelRecurringBooking(recurringBookingId, reason?)`:
  - `docs/transaction-schemas/cancel-recurring-booking-request.schema.json`:
    `{ recurringBookingId: string, reason?: string }`.
  - `docs/transaction-schemas/cancel-recurring-booking-response.schema.json`:
    `{ success: boolean }`.
  - Guards: booking MUST be non-company (no company assigned). Caller MUST be the
    booking's `customer` OR the independent manager assigned to serve it. Company-served
    bookings are rejected outright — this callable is not a company/company-manager path.
  - Server ONLY sets `recurring_bookings/{id}.status='cancelled'`, `cancelledAt`,
    `cancelReason`. No writes to any occurrence task.
- Customer surfaces (mobile app + `servido-website` `SeriesDetail.tsx`) and the
  independent `manager_panel`'s series detail (per `orders-recurring-gigs-manager-module`)
  each get a "Cancel series" control, gated by booking status (hidden once
  `cancelled`/`completed`) and non-company, calling the same `cancelRecurringBooking`
  callable. `company_panel`/`worker_panel` get no such control. Copy should make clear
  this only stops future occurrences, not any already-booked ones.

## Verification
Proof shows: (a) cancelling a series with several existing occurrence tasks in varied
states sets booking `status='cancelled'` and leaves every occurrence task completely
unchanged (no `isCancelled`, no `cancelRequest`, no field diffs on any task); (b) "Cancel
series" control is absent once the booking is already `cancelled` or `completed`; (c)
after series cancel, no new occurrence is generated by a later rolling top-up / monthly
materialization run.
